## 진짜 문제 (2026-08-12 사용자 확인 + 정정)

이 B2B 사이트는 **10개 미만 주문은 수동으로** 해야 한다. 구체적으로는
`상품페이지 → 제품구매하기 → 배송지 입력 → 예치금 '사용' → 결제하기` 5단계를 반복한다.

**왜 한 번에 못 묶나:** 주문마다 **수령인과 배송지가 다르기 때문**이다(고객 직배송).
장바구니는 한 주소로만 가므로 여러 배송지를 하나의 주문으로 합칠 수 없다.
다만 **같은 수령인이 2가지 이상 주문하는 경우**는 있고, 그때는 장바구니로 묶인다.

→ **주문 건수 = 배송지 개수.** 이건 몰의 제약이 아니라 업무의 본질이라 자동화로 못 줄인다.

## 그래서 자동화가 없애는 것

반복 **횟수**가 아니라 한 건당 드는 **손품**이다. 건당 사람이 하던 일:

| 작업 | 자동화 후 |
|---|---|
| 상품 페이지 찾아 들어가기 | 엑셀의 URL로 자동 |
| 옵션·수량 입력 | 자동 |
| **수령인·연락처·주소 타이핑** ← 제일 오래 걸림 | 자동 |
| 예치금 '사용' 클릭 | 자동 |
| 금액 확인 후 결제 | **사람** (남긴다) |

배송지가 5곳이면 사람은 **결제 버튼만 5번** 누른다. 나머지는 전부 자동.

## MVP 형태

**엑셀에 상품 URL·수량·수령인 정보를 적어 넣으면, 배송지별로 순차 처리하며
매 건 결제 직전까지 채워주고 사람이 결제하면 다음 건으로 넘어간다.**

같은 배송지에 상품이 여러 개면 장바구니로 묶어 **한 주문**으로 만든다.

## 이 선택이 왜 옳은가

앞서 API 경로에서 막혔던 문제들이 브라우저 자동화에서는 **존재하지 않는다.**

| API 경로의 벽 | 브라우저 자동화에서는 |
|---|---|
| 예치금 API 차감 불가 | 실제 결제 화면을 거치므로 **카페24가 정상 차감** |
| 주문 생성 API 없음 (migrations 우회) | 정상 주문 흐름 그대로 |
| 앱 등록·API 승인·개발권한 필요 | **아무것도 필요 없음** — 사장님 계정으로 로그인만 |
| access 2h / refresh 2주 토큰 갱신 운영 | 해당 없음 |
| rate limit(초당 2건) | 10건 미만이라 무의미 |

즉 [[architecture-decisions]]에서 "유력안 B(정상 결제 흐름)"라고 판단했던 것의
**가장 싸고 가장 확실한 구현체**가 브라우저 자동화다. API 경로는 규모가 커진 뒤의 선택지로 미룬다.

## 핵심 설계 원칙

- **🚨 MVP는 결제 버튼을 누르지 않는다.** 장바구니 담기 + 주문서 정보 입력까지만 자동화하고,
  **최종 결제는 사람이 확인 후 클릭.** 예치금이 잘못 빠지면 되돌리는 게 주문 취소 처리라 비용이 크다.
  자동화가 신뢰를 얻은 뒤에 마지막 클릭을 넘기는 순서로 간다.
- **셀렉터는 한 파일에 모은다.** 카페24 스킨은 몰마다·업데이트마다 DOM이 다르다.
  셀렉터가 코드 전체에 흩어지면 스킨이 바뀔 때마다 전수 수색을 해야 한다.
  (같은 교훈이 `cpotalecnt_order_pj`에도 있다 — "이카운트 UI의 CSS 셀렉터에 의존")
- **실패는 조용히 넘어가지 않는다.** 품절·판매중지·옵션 불일치로 담기가 실패했는데
  나머지가 성공해 주문이 나가면 **일부만 주문된 상태**가 된다. 라인별 성공/실패를 반드시 리포트.
- **멱등성.** 같은 엑셀을 두 번 돌려 중복 주문이 나가는 게 최악이다. 실행 이력을 남긴다.

## 예상 난관 (착수 전 인지)

1. **상품 옵션.** 옵션(사이즈/색상)이 있는 상품은 select를 골라야 하고 DOM 구조도 다르다.
   → 엑셀에 옵션 컬럼이 필요하다. 옵션 없는 상품과 분기 처리.
2. **상품 URL → 상품번호 파싱.** 카페24 URL은 보통 `/product/{이름}/{product_no}/category/...` 형태.
   `product_no`를 뽑아두면 URL이 조금 달라도 접근이 안정적이다.
3. **로그인.** 자동입력 방지문자(캡차)가 반복 실패 시 뜰 수 있음. 세션 재사용(쿠키 저장)으로 로그인 횟수를 줄인다.
4. **스킨 의존성.** 몰 스킨이 바뀌면 깨진다. 깨졌을 때 빨리 고칠 수 있는 구조가 안정성보다 중요하다.
