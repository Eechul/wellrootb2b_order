2026-08-12에 실제로 로그인해 DOM을 확인하고 전체 흐름을 끝까지 돌려본 결과.
셀렉터 자체는 `selectors.py`에 있다. 여기에는 **왜 그런지와 함정**만 적는다.

## 장바구니는 살아 있다 (다만 만능은 아니다)

- 상품 페이지에 버튼이 둘 다 있다: `product_submit(1, ...)` = 제품구매하기, `product_submit(2, ...)` = 장바구니담기
- 장바구니 페이지(`/order/basket.html`)는 **정상 작동**한다 — 전체상품주문·선택상품주문·수량변경·삭제 전부 있음

**⚠ 하지만 장바구니로 반복을 없앨 수는 없다.**
2026-08-12 사용자 정정: 상품마다 따로 주문하는 이유는 담기 버튼이 안 보여서가 아니라
**주문마다 수령인과 배송지가 다르기 때문**이다(고객 직배송). 장바구니는 한 주소로만 간다.

→ 따라서 **주문 건수 = 배송지 개수**이고, 장바구니는 *같은 수령인이 2가지 이상 주문할 때*만 묶는 용도다.
   자동화가 없앨 수 있는 건 반복 횟수가 아니라 **한 건당 드는 손품**(상품 찾기·수량·배송지 타이핑·예치금)이다.

## 함정 (실측으로 겪은 것들)

1. **`.basket_bt`를 클릭해야 한다.** 감싸는 `<a>`는 `display:inline`이라
   Playwright가 "not visible"로 판단해 클릭이 30초 타임아웃 난다. 안쪽 div를 클릭할 것.
2. **담기 성공 신호는 장바구니로의 리다이렉트.** 레이어가 뜨는 게 아니라 `/order/basket.html`로 이동한다.
   `wait_for_url("**/order/basket.html*")` 가 가장 확실한 판정.
3. **confirm 다이얼로그가 뜬다** — "장바구니에 동일한 상품이 있습니다. 추가하시겠습니까?"
   자동 수락하되 **메시지를 보관**해야 한다. 담기 실패 사유(필수 옵션 미선택 등)가 이 메시지로 온다.
4. **우편번호·기본주소가 `readonly`다.** 카카오 우편번호 위젯이 중첩 iframe
   (`#iframeZipcode` → `postcode.map.kakao.com`)에서 채우는 구조.
   위젯 DOM은 우리 통제 밖이라 더 취약해서, **값을 직접 넣고 읽어서 검증**하는 방식을 택했다.
   상세주소(`#raddr2`)만 일반 입력칸이다.
5. **연락처가 3칸으로 쪼개져 있다.** 앞자리는 select. `#rphone2_1`(휴대전화)에 **`0504`가 실제로 있다**
   — 안심번호를 쓰는 이 몰에서 중요하다. 일반전화 `#rphone1_1`에는 02/031/... + 050x + 070까지 있다.
6. **추가상품 옵션(`addproduct_option_id_*`)은 `[필수]` 표기가 있어도 미선택으로 담긴다**(실측).
   본품 옵션(`product_option_id_*`)이 있는 상품은 아직 못 만나봤다 — 만나면 검증할 것.

## 로그인 함정 — 이미 로그인된 채로 로그인 페이지에 가면 안 된다

세션이 살아 있는 상태에서 `/member/login.html`로 이동하면 **몰이 홈으로 되돌려보낸다.**
그러면 아이디 입력칸이 없어서 `page.fill()`이 **30초를 통째로 기다리다 죽는다**(실제로 겪음).

→ `ensure_logged_in`은 ① 홈에서 로그인 여부를 먼저 기다려 확인하고,
   ② 로그인 페이지에서 아이디 칸이 안 보이면 **로그인 상태부터 다시 확인**한다.
   고정 `wait_for_timeout` 대신 `wait_for_selector`를 쓰는 것도 같은 이유다(느린 화면에 강함).

## 예치금

- **예치금 전용 몰이다.** 주문서 안내 문구 그대로: *"예치금 구매를 제외한 모든 제품은 예치금으로만 결제 가능합니다"*
- 헤더에 보유 잔액이 노출된다(`/myshop/deposits/historyList.html` 링크 텍스트).
- 주문서의 예치금 '사용' 버튼은 `#all_use_deposit` — 스킨 JS가 텍스트를 "사용"으로 바꿔놓은 것이다.
  누르면 `#input_deposit`에 결제금액이 채워진다.
- 실측: 여주분말 60g ×2 = 8,474원 + 배송비 3,000원 = **11,474원**이 정확히 적용됐다.
- **적용 후 결제금액이 0으로 표시되는 건 정상이다.** 몰 안내 문구 그대로:
  *"예치금으로만 결제할 경우, 결제금액이 0으로 보여지는 것은 정상이며 [결제하기] 버튼을 누르면 주문이 완료됩니다."*
  → 뒤집으면 **적용 후에도 결제금액이 남으면 그만큼 예치금이 부족**하다는 뜻이다. 잔액 판정을 이걸로 한다.
  실측: 90,740원 주문 / 잔액 41,617원 → 적용 41,617원, 남은 결제금액 49,123원.

## 기타

- 배송비는 **차등(수량)** 방식. 3,000원 확인.
- 장바구니에 담긴 상품은 7일 보관.
- 배송메모는 `#omessage_select`(정형 문구) + `#omessage`(textarea) 조합.
- 결제하기는 `#btn_payment`. **이 도구는 절대 누르지 않는다** → [[mvp-browser-automation]]

## 🚨 주문서는 이전 값이 미리 채워져 있다 — 빈칸을 건너뛰면 사고다

'새로 입력'(`#sameaddr1`)을 골라도 **기본배송지와 최근 입력값이 그대로 남아 있다.** 실측 사례:

```
수취인 '(앞 주문의 수취인)' / 휴대전화 0504-xxxx-xxxx / 우편번호 4xxxx
기본주소 '(앞 주문의 주소)' / 상세주소 '(앞 주문의 상세주소)'
배송메모 '(최근 입력한 배송메모가 그대로)'
```

엑셀에서 빈칸인 항목을 "건드리지 않고 넘어가면" 이 값들이 **다른 수령인의 주문에 그대로 붙어 나간다.**
그래서 **엑셀을 진실의 원천으로 두고, 빈칸이면 화면도 비운다.**

- 배송메모 select에는 `(최근 입력) ...` 옵션이 **기본 선택**되어 있다. 비우려면
  `-- 메시지 선택 (선택사항) --`으로 되돌려야 한다.
- 배송메모 textarea(`#omessage`)는 select가 제어해서 Playwright의 `fill()`이 타임아웃 난다.
  **select를 먼저 맞춘 뒤 JS로 값을 넣을 것.**
- 휴대전화 앞자리 select에는 빈 항목이 없다 → 번호를 비우면 select는 남고 뒤 두 칸만 비워진다(문제없음).

## 주문서 필수/선택은 몰이 정해뒀다

`fw-filter` 속성이 곧 몰의 검증 규칙이다. 엑셀 필수 컬럼을 여기에 맞춰 놨다.

| 칸 | fw-filter | 판정 |
|---|---|---|
| 수취자 성명 `#rname` | `isFill` | 필수 |
| **수취자 전화번호** `#rphone1_2` | `isNumber&isFill` | **필수** |
| 수취자 핸드폰번호 `#rphone2_2` | `isNumber` | 선택 |
| 우편번호 `#rzipcode1` | `isLengthRange[1][14]` | 사실상 필수 |
| 나머지 주소 `#raddr2` | (없음) | 선택 |
| 배송 메세지 `#omessage` | (없음) | 선택 |

## ⚠ 시작 전 장바구니를 반드시 확인할 것

장바구니에 기존 항목이 남아 있으면 **전체상품주문에 함께 딸려 들어간다.**
실제로 첫 정찰 때 기존 1건이 있었다. 그래서 도구는 비어 있지 않으면 멈추고,
`--clear-cart`를 줘야만 비운다. 이 안전장치를 없애지 말 것.
