## 해결된 것 (2026-08-12)

1. **결제 방식 = 예치금 전용.** API 경로를 막은 사실이자, 브라우저 자동화가 옳은 이유. [[architecture-decisions]]
2. **거래처별 단가 없음** → 금액 계산 로직 불필요. 몰이 계산한다.
3. **알림톡·WMS 연동 없음.**
4. **"10개 미만 수동"의 정체** = 주문마다 수령인·배송지가 달라서(고객 직배송).
   → **주문 건수 = 배송지 개수.** 업무의 본질이라 자동화로 못 줄인다. 줄이는 건 건당 손품. [[mvp-browser-automation]]
5. **장바구니는 같은 수령인이 2가지 이상 주문할 때만 묶는 용도.** [[site-facts]]
6. **다중 배송지 순차 처리** 구현·검증 완료 (2배송지 3라인 테스트).
7. **예치금 잔액 부족 감지** 구현·검증 완료 — 90,740원 주문 / 잔액 41,617원에서 "49,123원 부족" 정확히 잡음.
   판정은 "예치금 사용 후 남은 결제금액 > 0". 예치금 전용 몰이라 이게 곧 결제 불가다.
8. **실행 이력(멱등성)** 구현·검증 완료 — 결제 확인된 배송지는 재실행 시 건너뜀.
   중복 방지와 "끊긴 발주 이어하기"가 같은 동작이 된다.
9. **셀렉터 전부 확보**, 실제 발주 엑셀로 결제 직전까지 완주 확인.

## 남은 과제

**A. GUI.** CLI가 안정됐으니 다음은 이것. 사장님이 직접 쓸 거면 필요하다.
Tkinter(파이썬 그대로) vs Electron(기존 `cpotalecnt_order_pj` 자산) 중 선택. [[stack-decision]]
엑셀 드래그 → 진행 로그 → 건별 "결제했음" 버튼 정도면 충분하다.

**B. 본품 옵션 상품.** 사용자 결정으로 **MVP 범위 밖**(2026-08-12).
지금 코드는 추가상품(`addproduct_option_id_*`)만 다루고, 본품 옵션(`product_option_id_*`) 상품을 만나면
담기가 실패하며 몰의 alert 메시지가 사유로 남는다. 나중에 필요해지면 그때 검증.

**C. 실전 검증.** 아직 **실제로 결제까지 해본 적이 없다.** 결제 후 장바구니가 정말 비워지는지
(= 결제 확인 판정이 맞는지) 첫 실전에서 확인할 것. 여기가 틀리면 이력이 어긋난다.
