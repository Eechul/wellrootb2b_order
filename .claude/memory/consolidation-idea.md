## 지금 흩어져 있는 같은 계열 프로젝트

- `wellrootb2b_order` (이것) — 웰루트 B2B, Python + Playwright, 예치금 결제
- `cpotalecnt_order_pj` — 이카운트 ERP 주문 자동입력, Electron + Selenium
- `sello_auto_order_processing` — 셀로/공유넷 주문 엑셀 변환, Python/Tkinter
- `my_order_management`, `kh_balju_server` 등도 발주 계열

스택이 제각각(Playwright / Selenium / 변환 전용)이라 지금은 코드를 그대로 옮겨 쓰기 어렵다.

## 이미 공통인 것 vs 사이트마다 다른 것

이 프로젝트를 만들면서 **경계가 꽤 선명해졌다.** 통합한다면 이 선을 그대로 쓰면 된다.

| 공통 (그대로 재사용 가능) | 사이트마다 다름 |
|---|---|
| `excel_reader` 파싱·검증·배송지 그룹핑 | `mall_selectors` 셀렉터 |
| `report` 라인별 성공/실패 | `steps/` 담기·주문서 절차 |
| `history` 멱등성·이어하기 | 결제 방식(예치금/무통장/카드) |
| `credentials` DPAPI·키체인 | 엑셀 컬럼 매핑 |
| `updater`·`build.ps1` 배포 | 주문 단위 규칙(배송지 1곳/주문 등) |
| `app.py` GUI 껍데기, `runner` 흐름 | |

→ 통합의 모양은 **공통 코어 + 사이트별 어댑터**다. 사이트별로 exe를 따로 뽑든,
하나의 exe가 어댑터를 골라 쓰든 둘 다 가능하다.

## 판단 기준 (섣불리 합치지 말 것)

- **2~3개면 통합 이득 < 추상화 비용.** 두 번째 사이트를 실제로 붙여봐야 공통부가 드러난다.
  지금 미리 일반화하면 틀린 추상화를 만든다.
- **위험 격리를 잃는다.** 지금은 한 사이트가 깨져도 다른 프로그램은 멀쩡하다.
  합치면 공통부 버그가 전 거래처로 번지고, 한 곳 고치자고 전체를 재배포해야 한다.
- **배포 대상이 다르다.** 이건 거래처 사장님들께 나가고, 다른 건 사내용일 수 있다.
  같은 exe에 묶으면 안 쓰는 기능까지 보인다.

## 통합보다 먼저 할 만한 것 (이득이 크고 위험이 작음)

**셀렉터를 코드에서 빼내 원격 설정으로 두는 것.** 지금은 몰이 스킨을 바꾸면
`mall_selectors.py`를 고쳐 **exe를 다시 빌드·배포**해야 한다.
셀렉터를 JSON으로 빼고 `updater`가 그것만 갱신하면, 재배포 없이 몇 분 만에 고칠 수 있다.
프로그램이 늘어날수록 이 이득이 커지고, 통합 여부와 무관하게 유효하다. → [[distribution]]
