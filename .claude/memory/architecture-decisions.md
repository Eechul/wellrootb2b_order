> **2026-08-12 최종 결론: MVP는 브라우저 자동화(경로 D).** 아래 A/B/C 비교는 거기에 도달한 과정이고,
> 나중에 규모가 커져 API를 다시 검토할 때 읽을 기록이다. 현재 방향은 [[mvp-browser-automation]].
>
> **경로 D — 브라우저 자동화**: 사장님 계정으로 로그인해 실제 화면을 클릭한다.
> 정상 결제 흐름을 그대로 타므로 **예치금·재고·가격이 전부 카페24 처리**. 개발권한·앱등록·토큰갱신 불필요.
> 아래 B(장바구니+정상결제)가 노렸던 정합성을 훨씬 싸게 얻는다. 대가는 스킨 DOM 의존성뿐이고,
> 10건 미만 규모에서는 rate limit·성능이 전부 무의미하다.

## 확정: 중계 서버는 선택이 아니라 필수

카페24 Admin API 토큰은 **몰 단위 전체 권한**이다. 거래처 사장님에게 Client ID/Secret이나 토큰을 주면
그 사장님이 **전체 고객 정보·타사 발주 내역·전체 매출**을 조회·수정할 수 있다.
스코프를 거래처 단위로 쪼갤 방법이 카페24 쪽에 없으므로, **권한 분리는 우리 서버에서만 가능**하다.
카페24 자격증명은 서버 밖으로 절대 나가지 않는다. 이 판단은 아래 경로 선택과 무관하게 유효하다.

## 주문을 카페24에 넣는 3가지 경로

| 경로 | 장점 | 잃는 것 |
|---|---|---|
| **A. `POST /orders/migrations`** (이전몰 주문) | 완전 자동, 사람 개입 0. 진짜 "발주 API 키" 모델이 가능 | **예치금이 차감되지 않음(치명)**, 쿠폰·등급할인 미적용, '과거 데이터' 성격, 정식 용법 아님 |
| **B. Front API `POST /api/v2/carts` + 정상 결제** | 예치금 차감·주문 생성이 카페24 내부에서 원자적 처리 → **잔액 정합성 공짜** | 사장님이 마지막에 결제 버튼 클릭 필요. 브라우저 세션 기반일 가능성 → 서버-투-서버 API 아님 |
| **C. 발주는 우리 DB, 카페24는 정산 시 일괄 반영** | 카페24 제약에서 자유로움 | 카페24 어드민이 진실의 원천이 아니게 됨. 예치금 장부 이중관리 |

## 2026-08-12 판단: B 경로가 유력, A는 사실상 막힘

운영자 확인 결과 **① 예치금 위주 결제 ② 거래처별 단가 없음(전부 동일) ③ 알림톡·WMS 연동 없음**.
이 세 답이 저울을 완전히 기울였다.

- **②③은 A의 단점을 지웠다.** 단가표를 우리가 재구현할 필요 없고, 끊길 알림톡·WMS도 없다.
- **그런데 ①이 A를 죽인다.** 예치금 잔액은 API로 증감할 수 없다([[cafe24-api-constraints]] 4항).
  A로 주문을 넣으면 주문은 생기는데 **예치금은 그대로 남는다** → 사장님이 잔액 없이 무한 발주 가능.
  예치금 몰에서 이건 버그가 아니라 사고다.
- **동시에 ②는 B의 마지막 단점을 지운다.** 단가가 전부 같으므로 우리가 금액을 계산할 이유 자체가 없다.
  카페24 정상 흐름에 태우면 가격·재고·예치금이 전부 알아서 맞는다.

**결론: 우리가 만들 것은 "주문을 대신 생성하는 서버"가 아니라 "발주를 대량으로 조립해 정상 결제 흐름에 태워주는 레이어"다.**

### A를 굳이 살리려면 (운영자 합의 필요)

셋 다 대가가 크다. 먼저 합의 없이 구현 착수 금지.
1. 운영자가 어드민에서 예치금 **수동 차감** → 발주 건수만큼 수작업, 자동화 취지 상실
2. 예치금 → **적립금(points)으로 운영 전환** → `POST /api/v2/admin/points`로 차감 가능하나 회계·세무 취급이 다름
3. 예치금 장부를 **우리 DB에서 별도 관리** → 카페24 어드민 잔액이 무의미해짐(이중장부)

## 원래 목표와의 차이 — 솔직하게

사용자의 처음 구상은 "사장님들에게 발주 API 키를 발급"이었다.
**예치금 몰에서는 이 모델이 그대로 성립하지 않는다.** B 경로는 사장님 로그인 세션 기반이라
키 발급 대신 **로그인 자체가 인증**이 된다. 서버-투-서버 API는 예치금 정합성과 맞바꿔야만 얻어진다.

다만 **원래 목적(사장님이 발주를 편하게 하는 것)은 B로 충분히 달성된다.**
엑셀 업로드 → 장바구니 자동 조립 → 결제 클릭 한 번. 체감 편의의 대부분은 여기서 나온다.
"API 서비스"라는 형태에 집착하지 말고 **발주 편의 + 락인**이라는 목적을 볼 것.

## 현실 점검: API보다 발주 화면이 먼저다

도매 사장님 대부분은 자체 ERP에서 API를 호출할 능력이 없다.
실사용은 거의 확실히 `웹 발주 화면 + 엑셀 업로드`에서 나오고, API 직호출은 큰 거래처 소수다.
(사용자의 기존 프로젝트 `sello_auto_order_processing`, `cpotalecnt_order_pj` 모두 엑셀 기반 발주라는 점이 방증)
→ B 경로가 이 현실과도 더 잘 맞는다.

## 경로와 무관하게 서버가 책임져야 하는 것

- **멱등성** — 거래처 발주번호 기준 idempotency key. 재시도로 중복 발주가 꽂히는 게 이 도메인 최악의 사고.
- **거래처 격리** — A 키/세션으로 B의 주문·내역이 보이면 안 된다.
- **토큰 단일 갱신 주체** — 여러 인스턴스가 동시에 refresh 하면 서로 무효화된다. [[cafe24-api-constraints]]
- **큐 + 백오프** — rate limit 대응.
- (A 경로일 때만) 금액 계산 — B에서는 카페24가 계산하므로 불필요.
